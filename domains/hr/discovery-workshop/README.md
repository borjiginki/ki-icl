A discovery workshop is how KI group turns a client's stated problem into a scoped piece of work.
It runs before any estimate is given, and its output is what an estimate is built on.

## When to run one

Run a discovery workshop when at least one of these is true:

- The client has described an outcome but not a system.
- Two people on the client side describe the problem differently.
- The work touches a system nobody on our side has seen.

Do not run one when the client has an existing specification that our team has already reviewed and accepted.
In that case the workshop produces nothing that the specification did not already settle.

## Who attends

| Role | Side | Why they are needed |
|---|---|---|
| Facilitator | KI group | Runs the room, owns the agenda, does not advocate for a solution |
| Solution lead | KI group | Tests feasibility in real time |
| Business owner | Client | Can say what the outcome is worth |
| System owner | Client | Can say what the current system actually does |

The workshop does not run without a client-side system owner in the room.
Without one, every constraint recorded is a guess, and the estimate built on it is a guess too.

## The four phases

1. **Frame.** Agree in one sentence what would be true if this work succeeded. Write it on the wall and leave it there.
2. **Map.** Draw the current system as it is, not as anyone wishes it were. Every box gets a named owner.
3. **Cut.** Identify what is in scope for a first delivery. Everything else goes on a parked list that is read back aloud before the session ends.
4. **Commit.** Name the risks that could change the estimate by more than a third, and say who will resolve each and by when.

## What is produced

A discovery workshop is not finished until these three exist:

- A one-page problem statement, agreed in the room.
- A current-state map with named owners.
- A risk list where every entry has an owner and a date.

If any of the three is missing, the workshop has not concluded and a second session is scheduled.
